# Registration-to-terrain follow-up

This follow-up checks the remaining island-card joins: the `UIMapSelectHandling` result, the native page/layout path, the four card previews, and their relationship to `FieldMainFieldParam` and LandMaking data. It supplements [the registration/terrain proof](REGISTRATION_TERRAIN_PROOF_20261107.md) and its [machine-readable record](../output/gameplay/registration_terrain_followup_20261107.json). Evidence labels retain that report's meanings: `EF`, `TBL`, `STRUCT`, `PSEUDO`, `NATIVE`, `CAT`, and `OPEN`.

The eventflow proves that the map-selection action returns a value saved under `cVillage`. Static native evidence now gives a stronger candidate path from `MapSelectPage` to `CharaMakeMap`, including a helper that passes the literal layout name into a resource-loading routine. The registration record still maps `cMapSelect` only to a normalized class-name candidate, however, and the helper's callback ownership is not resolved. The card assets expose four copies of one generic card layout and a generic capture texture, with no card or preset IDs. The `cVillage` result therefore cannot yet be joined to a selected field preset or its LandMaking BYML.

## Presets, LandMaking, and the unresolved selection join

Base data source `B_data/Bcsv/FieldMainFieldParam.bcsv` (ID 41, SHA-256 `3ebd1057e41b0666aa30c6d8beee9220b52d8fb5280c478e8eb13eaca5d27944`) has 96 rows. The decoded table crosswalk shows ordinary fields such as `UniqueID`, `FieldData`, `OutsideTemplateKind`, `Label`, `StructureData`, and `ItemData`. For example, `UniqueID:0` has `FieldData:FieldPresetA00`; the matching `FieldPresetA00_LandMaking.byml` is source 2442 (SHA-256 `cba1ab90d21982b443e719e30a19c80fa9aa9ead86f03705f5ecbd3c821d4aca`). This exact data-name join is `TBL` evidence for which LandMaking file belongs to that table row.

The separate static generator audit reports four repeated source-row/template setup slots in function `0x529910` and calls to `0x528bf0`; `0x552bb0` selects an outside-template `UniqueID` from `FieldOutsideTemplate` (source 46, 36 rows; SHA-256 `1c615f1c8b42d4f690f81fd577261a3daf61f814bb3b1f93354fd1b714c5a314`). The generator's parent functions were not executed end-to-end in that audit. Its four generation slots and the UI's four visual cards share a count, but no card ID, `cVillage` payload, `FieldMainFieldParam.UniqueID`, `FieldData`, or `*_LandMaking.byml` reference is joined across the two code paths. The count match is not a mapping.

The precise remaining terrain/save gap is therefore: recover the `UIMapSelectHandling` controller/output path; identify the runtime value that feeds each `LMapChoice.P_Map_00`; recover the selected value's mapping to a row in `FieldMainFieldParam`; then identify the `cVillage` result-to-save writer. Until those edges exist, the four cards cannot be assigned to preset IDs or LandMaking sources. The `EF` `SaveSetFromUIResult {SaveType:cVillage}` call proves the named EventFlow handoff only.

For a Godot-facing asset pipeline, preserve the four original card transforms and nested part hierarchy, decode the actual BNTX channel-source/block-compression metadata instead of treating texture names as RGBA assets, and represent `Capture^t` as a runtime-fed texture only after its producer is identified. Keep the BFLAN tracks as generic pane/material animation data until their page callbacks are known. The `FieldData`/LandMaking name join can be represented as source data, but do not wire it to a card until the missing runtime result mapping is recovered. No Godot implementation or build was performed.
