# UI/HUD lifecycle, input routing, and renderer flags

Status: 6 November 2026. Source build: ACNH 1.0.0 ExeFS `main`, SHA-256 `f8d248109ff72999b4600ae3749f8c7397fb960f7ad3ab8dee3018ae9e14e900`. This follow-up reads the available native image, the shared read-only index, and committed RomFS-derived catalogue records. It does not contain a synchronized game capture.

## Page loader and lifecycle

`[NATIVE STATIC + RELOCATION]` The catalogue still contains 135 page factories following the common constructor/registration pattern. Each observed page pointer sequence has slot 46 (`+0x170`) relocated to a unique three-instruction string getter; 134 return a name that matches a catalogued BFLYT and `SwkbdPage` returns `SwkbdDummy`. The page audit finds no direct `B`/`BL` instruction to any of the 135 getter targets. This proves a page-to-identifier crosswalk, not that a scheduler calls the getter or passes its result to the layout loader.

`[NATIVE STATIC]` All 135 factories call the shared registration helper `0x1da8220`. It calls `0x1da40b0`, which writes `2` at page object `+0x48` and branches through page slot 5 (`+0x28`) to `0x1da5380`; it then inserts an intrusive-list node and increments a collection count. The earlier helper `0x1da8210` writes `1` at the same offset. Those are observed values and transitions; the field is not identified as an open, active, or visible state.

`[NATIVE STATIC + INDEX]` A direct-call ordering check across every catalogue factory finds the same sequence in all 135: helper `0x1da8210` (store 1 at `+0x48`), common page initializer `0x1144600`, then registration `0x1da8220` (store 2 at `+0x48`, virtual slot 5 and collection insertion). No conditional or unconditional branch occurs between those callsites in any of the 135 factory functions. This proves a straight-line construction transition, but the numeric values remain unnamed.

`[NATIVE STATIC + POINTER INVENTORY]` A second path creates the native-string `RootPage`. Method `0x1dd4090` allocates `0x1c8` bytes, calls constructor `0x1da5b50` (whose indexed string reference is `RootPage`), stores the object at owner offset `+0x448`, then calls `0x1da40a0` and `0x1da40b0`. The constructor initializes the same page field `+0x48` to 0; those helpers write 1 and 2 in order. The latter also dispatches through the new object's slot `+0x28`. The code-pointer inventory places `0x1dd4090` at slot 10 of sequence `0x31e0ba0`, but labels the sequence only as relocated code pointers; there are no indexed direct callers, so its virtual dispatch interpretation is not established. This path calls the state-2 helper directly and does not call collection inserter `0x1da8220`.

`[NATIVE STATIC]` The shared numeric field has further concrete transitions, still without semantic names. `0x1da7030` proceeds only from state 1, stores 2, and updates a pending-work mask; `0x1da7150` handles states 0, 2, and 5, checks child-resource conditions, and can return state 2 to 1. The related finish/close helpers show additional values: `0x1da4890` stores 4 and recursively invokes page callbacks; `0x1da4210` moves states 4/6→5, 3→2 after list removal, 5→7, and 2→8 before calling `0x1da43d0`; that finisher turns 4/6→3, 5→2 after unlinking, and 7→8 after unlinking and a virtual call. These are raw state transitions, not evidence that the integers mean open, active, closing, or visible.

`[NATIVE STATIC + POINTER INVENTORY]` The same sequence `0x31e0ba0` contains `0x1dd4390` at slot 12 and `0x1dd43a0` at slot 13; they tail-branch to `0x1da4890` and `0x1da43d0`. Slot 22 (`0x1dd43b0`) calls `0x1da4cd0` on the `RootPage` at `+0x448`, then calls `0x1da7030` and `0x1da7150` on a separate page object at `+0x420`. There are no indexed direct callers of slot-22 function `0x1dd43b0`; its body connects page-tree callbacks and numeric processing, but does not establish an outer scheduler or tick cadence.

`[NATIVE STATIC + INDEX]` One callback route into the `RootPage` tree is directly indexed: function range `0x1c805d0` calls `0x1dd4560` at `0x1c80670` and tail-branches to `0x1dd44c0` at `0x1c806ac`. Both pass a context to `0x1da4db0` on the object at `+0x448`. That helper returns for state 3; otherwise it walks the child list and calls slot `+0x78` on each page. The exact event meaning and the route that schedules `0x1c805d0` remain unknown.

The only indexed direct caller of candidate selector `0x1da8270` is `0x1cbac50`. That selector walks a collection, calls page slot 17 (`+0x88`), whose common thunk forwards to slot 30 (`+0xf0`), and returns an entry address when the result bit is set. This is a selection predicate for a candidate collection entry; the available code does not connect it to slot 46, a page scheduler, or a global open/close/back stack. Loader handoff, page update scheduling, modal order, focus restoration, and page teardown remain unresolved.

## Npad to action route

`[NATIVE STATIC + INDEX]` The Npad update method `0x1968b80` has eleven direct `BL` targets in the indexed call table and no direct call to the generic UI action dispatcher `0x14845a0`. The dispatcher has 28 indexed direct callsites, but these alone do not identify which platform input or scheduler reaches them. Npad sampling, the 13 named UI action IDs, and the separately mapped touch-to-target-control path are not statically joined. A virtual callback or intermediate state translation could still connect them.

## Hit-pane identity and declared visibility

The controller constructor and the separate controller-side `Hit` binding use the same dynamic name source, lookup context, descriptor base, helper, and literal token `Hit`. The first lookup result is stored at inline hit node `+0x20`; the second is stored at controller `+0x420+0x70`. Native code does not compare those returns. The asset catalogue gives 18 same-layout `B_Hit` BND1 / `B_Hit:Hit` CNT1 pairs, and all 18 BND1 records declare `visible=true`. This strengthens the static name crosswalk, but the dynamic prefix and an instance pointer comparison are absent.

The BFLYT catalogue also contains two `ScissorPane` records, `S_Scissor_00` and `S_Scissor_01` in `LMyDesignEditCanvas`; both declare `visible=true` and size 650×650. These are serialized asset properties, not current runtime flag values.

## Renderer gates and ScissorPane bounds flag

`[NATIVE STATIC]` The ScissorPane factory `0x14c89c0` allocates through two branches, and both call base Pane constructor `0x192d3d0` (`0x14c89f0` and `0x14c8a34`). That base constructor initializes byte `+0x58` to `0x11` and zeros the halfword beginning at `+0x5b`; these defaults fail the generic renderer gate below. The later call to `0x14c8a90` at `0x14c8a78` is the auxiliary-object constructor and must not be mistaken for the factory's base Pane call. A raw flag-copy candidate `0x192d490` copies source bytes `+8` and `+0xb` to renderer fields `+0x58` and `+0x5c`, respectively, but the shared direct-call index has no caller for it, and no static edge ties it to the ScissorPane layout path. `VisibleOn`/`VisibleOff` string references occur in page functions `0x1258d10` and `0x12ece60`, both of which call helper `0x1683190`; no recovered write connects those labels to these renderer bytes.

The generic pane renderer `0x192fb20` calls a pane vtable callback at `+0xa8` only when its raw object checks pass: byte `+0x58` has mask `0x81` set, byte `+0x5c` has bit 4 set, byte `+0x5a` is nonzero, and byte `+0x62` has bit 1 clear. It later traverses child panes through slot `+0xa0`. The instructions expose these byte tests but do not label them as active-state names. The hit visibility helper `0x14c80d0` also checks bit 0 of pane byte `+0x58` and can walk ancestor panes according to its input options. No linked producer has been found for the instance flag values required by the generic callback gate.

The ScissorPane setter `0x14c8d00` stores `1` in byte `+0xe0` and copies four 32-bit bounds to `+0xf0..+0xfc`. Its render callback `0x14c8d30` uses those stored values when `+0xe0` is nonzero; when it is zero, it derives a rectangle from the pane transform. Both branches reach the scissor-stack push call at `0x14c8e44`. Thus `+0xe0` selects the source of bounds; it does not disable the clipping callback. Native stack bookkeeping was exercised by the existing 11-case synthetic fixture, which stubs the push/apply boundaries and does not issue NVN commands.

The only raw pane-flag copy candidate found so far, `0x192d490`, copies source bytes `+8` and `+0xb` to object bytes `+0x58` and `+0x5c`. It has zero indexed direct callers and no membership in the available relocated pointer inventory (18,348 sequences, 192,637 entries). The page functions with `VisibleOn`/`VisibleOff` string references call generic helper `0x1683190`, whose indexed body builds descriptor/callback lists; it has no direct store to these pane bytes. A callback or runtime route may still exist, so the flag producer and live instance values remain unresolved.

`[NATIVE STATIC + API RESOLUTION]` The push helper `0x14c8fe0` intersects incoming left/top/right/bottom bounds with the current top entry. If the intersection is inverted on either axis, it replaces all four values with zero, then applies the result in mode 1 and stores it when the prior stack count is at most five (six saved rectangles). At count six, another push still applies its intersection but exits without saving or incrementing the stack. The restore helper `0x14c9250` decrements the count and reapplies the previous entry in mode 1; on an empty stack it applies a zero rectangle in mode 0. In `0x14c90e0`, mode 1 reaches separate viewport/depth (`0x19a9c60`) and scissor (`0x19a9d50`) updates, while mode 0 reaches the combined update (`0x19a9960`). The two paths resolve through the GOT cells associated with the `nvnCommandBufferSetViewport` and `nvnCommandBufferSetScissor` strings. This traces submission of transformed rectangles into native NVN calls; it does not prove the GPU's pixel coverage. In particular, the empty-stack logical zero rectangle still passes through the live viewport/coordinate transform, whose runtime values and displayed result were not captured. The existing fixture does not exercise balanced traversal beyond six saved entries.

The separate parent-bound pointer at hit node `+0x28` is inherited under node flag `0x40` and participates in hit-rectangle intersection. Native does not call that field a render clip. The ScissorPane render path is direct static evidence for scissor submission, but which callback flags and bounds are active for a live BFLYT instance, the resulting pixel coverage, and framebuffer origin remain unmeasured.

## Evidence boundary

The current worktree has the ExeFS `main` input and committed RomFS-derived catalogue JSON, but no raw RomFS archive under `inputs/`. The static pass now maps RootPage construction, callback propagation into its child tree, and numeric `+0x48` transitions; no direct scheduler call or semantic state label is recovered. No synchronized live capture aligns page events, Npad samples, dynamic controller parameters, live pane pointers, renderer flag values, viewport origin, or GPU output. The only flag-copy candidate has no indexed direct caller or pointer-sequence membership, and the label references do not establish a producer. The NVN math maps logical bounds into runtime target-pixel bounds and truncates to integer origin/size, but there is no captured target rectangle or pixel coverage. These limits prevent stronger scheduler, live flag, framebuffer-origin, and clipping claims from the available dump/index records alone.
