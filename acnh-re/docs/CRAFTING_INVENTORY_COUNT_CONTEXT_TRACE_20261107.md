# A/B/C Inventory Count Manager Context Trace

**Build:** Animal Crossing: New Horizons 1.0.0. **Status:** source-backed control-flow/layout trace plus audit of existing bounded native fixtures. No new native execution, live save, build, or save mutation is claimed.

Evidence labels: [SRC] indexed pseudocode/direct-call evidence, [NATIVE] original ELF instructions executed in a bounded sandbox, [FIXTURE] reconstructed data or manager context, and [OPEN] unproved runtime binding.

The source points to a lazy global manager. At 0x96ef0, callsite 0x97694 invokes 0xed87d0. That routine checks global 0x33d3ce0; when empty, it allocates an 0x8f348-byte manager object, initializes its base subobject, invokes 0xed8870, then publishes the pointer. The constructor clears the ready byte at manager+8 and installs the three component vtables. No located native fixture calls this factory or constructor.

The manager's three counter components occupy adjacent regions: A starts at +0x10, B at +0x7838, and C at +0xf060. Their counter arrays begin at root offsets +0x308, +0x7b30, and +0x23020. Each array has 15,000 u16 counters. Keep the source-record count separate from the count field copied into the component: A/B loaders read their source count at source+0xa0 and store it at component+0xb0; C reads source+0x9c40 and stores it at component+0x9c50. The A/B loaders copy at most 20 item words and scan up to 20; C copies 5,000 item words and scans up to 1,600. The A/B source records also carry metadata after the count field. This trace disambiguates those offsets because the source offset is not the component field offset.

The cold path is visible in both 0xed9c20 and 0xee0be0. Each obtains a player context, resolves three member descriptors at player-relative +0xe0, +0xa8, and +0x150, passes their source bytes to 0xeda040, 0xeda160, and 0xeda280, then sets manager+8. The loaders reset their slot-list state, clear 30,000 bytes of counters, and dispatch through their component vtables to the original producers. In 0xedc240, 0xed9c20 is called at 0xedc688 and 0xee0be0 is called at six recipe-material sites. The latter reads per-item A/B and optional C counters, writes availability fields, and clears the recipe sufficiency byte when a requested amount is not met; its check does not subtract materials.

Existing fixtures cover parts of this path:

- [NATIVE] `tools/inventory_cache_native.py` exercises the original A/B/C loaders and producer callbacks with source-layout fixture records and real ItemParam/ItemKind table data. Its 722 bounded cases cover 264 A, 264 B, 98 C, and 96 producer-to-requirement checks with zero mismatches. It reconstructs component vtables/layout and node pools directly; it does not call the global factory, acquire a real save wrapper, or invoke the cold parent path of 0xee0be0.
- [NATIVE + FIXTURE] `tools/crafting_transaction_followup_native.py` runs recipe 56 through the original cold 0xee0be0 path. It reconstructs the three member descriptors and source records, then calls the original loaders/producers and requirement checker. With fixture counts [2, 2, 1], all five one-unit fruit materials pass; excluding C or omitting Peach from C makes Peach insufficient. Only the SDK memset import is emulated as a byte-accurate callback. The fixture demonstrates native cold population and checking over reconstructed inputs, not a real save or ingredient removal.
- [NATIVE + FIXTURE] `tools/crafting_transaction_manager_followup_native.py` separately calls original 0xee1060 for recipe 56 and probes 0xf9e410's Apple gate. Its synthetic pocket/player view has one item record per material but no A/B/C counters. The 0xee1060 scratch list at context+0x2a550 is initialized separately from the cache fixture; the same run does not cold-load A/B/C or call 0xee1420. Two view-service virtual methods are success stubs. The Apple 0xf9e410 probe uses the corrected dense ItemParam index and observes SaveCountMaxNum=0, so the original helper returns early without writes for that fixture.
- [NATIVE + PATCHED PREDICATE] Existing signed-delta leaf cases for 0xf9e410 patch the 0xaac730 acceptance result to true and therefore establish only the subsequent write algorithm. They do not demonstrate an accepted real stack/count context.

The cache layout ends its C component at manager+0x2a550, the same numeric offset used by 0xee1060 for its scratch/list structure. This adjacency is source-backed, but no existing fixture installs the cold A/B/C cache and runs the 0xee1420-to-0xee1060 path with one shared, source-authentic player context. Do not treat the adjacency alone as proof that a tested pocket record supplied the counters.

The 0xf9e410 path is distinct: its only direct caller is 0xeff060. It receives a pocket-slot list, an item descriptor, and a signed delta; it first calls 0xf9e840, which gates its slot scan and count writes using the item-kind SaveCountMaxNum predicate. The decompilation exposes no A/B/C cache argument or direct counter lookup in this path. The existing Apple fixture proves only the zero-predicate early branch for the tested reconstructed object. It does not show that crafting rejects Apple or that Fruit is non-stackable: the separate MultiHoldMaxNum field is 10 and is used by the bounded inventory-counter producer.
