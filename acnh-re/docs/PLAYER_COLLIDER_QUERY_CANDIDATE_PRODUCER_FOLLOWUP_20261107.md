# ACNH 1.0.0 query-list and candidate producer follow-up

This bounded follow-up traces ownership and producers for the world query list consumed by `0x7bccf0` / `0x7c5570`. It does not run Godot or a build, patch a synthetic world root, or treat the earlier native-emulator fault as gameplay behavior. The executable identities remain ELF SHA-256 `5bf707c3dc5dac0ad9635af7d336ec580f81c3f7876d0f55400d1900e3415d74` and ExeFS `main` SHA-256 `f8d248109ff72999b4600ae3749f8c7397fb960f7ad3ab8dee3018ae9e14e900`.

## Result

The native source does contain explicit producers for the intrusive list iterated by `0x157270`. The world subobject constructor `0x156840` initializes that query list empty; `0x157060` inserts candidate nodes, and `0x1571e0` removes them. `0x1868c0` / `0x1868e0` wrap those operations through the world singleton. One producer constructs and self-registers a spatial-index object (`0x156e30`, called by `0x1978a0`); other direct insertion callers register embedded or heap-allocated volume-shaped objects (`0x56eb80`, `0xc74610`, `0xc74970`). These code paths prove list mechanics and candidate creation patterns, but they do not establish the live island’s list contents or the callback implementation invoked at candidate vtable slot `+0x30`.

The query root remains unavailable in the native fixture. Root constructor `0x197740` allocates a `0xf88` object and calls `0x156840` for `root+0x28`; it leaves `root+0xa0` (the query context’s `+0x78` grid pointer) and `root+0xf10` readiness byte zero. The helper `0x1978a0` clears `root+0xf60` and calls `0x156e30`, but it has no indexed direct callers, so the indirect lifecycle dispatch is still not traced. The prior constructor probe stopped at an allocator/import bootstrap fault with a null target; this is a sandbox fixture limitation, not an in-game error. See the previous [root initialization follow-up](PLAYER_COLLIDER_QUERY_INIT_FOLLOWUP_20261107.md).

### Candidate-producing paths

- `0x156e30` constructs the query context’s spatial-index object. It creates a `0x118` object, initializes it with `0x172090`, sets dimensions and storage through `0x1725f0`, assigns it to context `+0x78`, then self-inserts it into the `+0x48` query list and increments `+0x58`. In the default branch dimensions are `0x40 x 0x40`; a selected alternate is `0xa0 x 0xa0`. `0x1978a0` is its only indexed direct caller and clears root `+0xf60` before calling it. The live indirect call into `0x1978a0` is OPEN. See [0x156e30](../../../acnh-re/output/binary/analysis_decomp/156e30.c), [0x172090](../../../acnh-re/output/binary/analysis_decomp/172090.c), [0x1725f0](../../../acnh-re/output/binary/analysis_decomp/1725f0.c), and [0x1978a0](../../../acnh-re/output/binary/analysis_decomp/1978a0.c).
- `0x56eb80` registers an embedded candidate at object `+0x58` or `+0x240`, selected by flags. Constructor `0x56e830` initializes the first with `0x1711d0` and the alternate with `0x171bc0`; `0x56f260` invokes `0x56eb80` when the candidate object’s flag is set, and `0x573e00` reaches `0x56f260` on its selected record path. This proves an actor/object-driven candidate registration path in code, but not which island objects activate it at runtime. See [0x56e830](../../../acnh-re/output/binary/analysis_decomp/56e830.c), [0x56eb80](../../../acnh-re/output/binary/analysis_decomp/56eb80.c), [0x56f260](../../../acnh-re/output/binary/analysis_decomp/56f260.c), and [0x573e00](../../../acnh-re/output/binary/analysis_decomp/573e00.c).
- `0xc74610` allocates four `0x1e8` nodes, initializes each with `0x1711d0`, writes box-like dimensions/positions around bounds returned by its helpers, applies flags (`0x170ff0(node, 0x800)` and node field `+0x44 = 0x200000`), stores accepted pointers in the owning object’s array, and registers each through `0x1868c0`. It has no indexed direct caller, so its runtime dispatcher/owner is OPEN. See [0xc74610](../../../acnh-re/output/binary/analysis_decomp/c74610.c) and [0x1711d0](../../../acnh-re/output/binary/analysis_decomp/1711d0.c).
- `0xc74970` allocates and registers one similarly initialized volume-shaped node. Its source references the `Entrance` label while resolving data-derived bounds. Its indexed caller is `0xc3baa0`; cleanup helper `0xc744a0` removes stored candidates through `0x1868e0` and calls each candidate’s destructor slot `+0x18`. These fields support a volume/candidate classification, not a claim about exact in-game collision behavior. See [0xc74970](../../../acnh-re/output/binary/analysis_decomp/c74970.c), [0xc3baa0](../../../acnh-re/output/binary/analysis_decomp/c3baa0.c), and [0xc744a0](../../../acnh-re/output/binary/analysis_decomp/c744a0.c).

The registered nodes have vtable bases initialized from relocated globals by `0x1711d0` or `0x171bc0`. The actual target at slot `+0x30` used by `0x157270` is not resolved in the static call index. Therefore the source proves that nodes are created and offered to the query list, but not the exact candidate response, terrain/collider combination rule, or returned ground/movement result.

## What remains OPEN

A faithful `0x7bccf0` / `0x7c5570` fixture still needs all of the following from a traceable original initialization path: the constructed world object at singleton `0x32d0de8`; live `root+0xa0` grid pointer and `root+0xf10` readiness; invocation of the spatial-index lifecycle method `0x1978a0`; loaded grid and backing arrays; query-list population with correctly linked candidate nodes and their real relocated vtables; and the runtime dispatcher/load path that owns the `0xc74610`/`0xc74970` candidate sets. The fresh Sandbox lacks the original allocator/import target required by the constructor, so substituting a hand-built root/list would only test guessed layouts. No full query was rerun.
