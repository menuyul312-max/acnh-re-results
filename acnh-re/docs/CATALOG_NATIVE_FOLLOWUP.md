# Catalog Bitset Native Follow-up

## Proven setter behavior

The native function at `0xeecad0` is the item catalog bit setter. It first calls `0xab2940` with the supplied item ID; the mapper's result is then used as the catalog bit index. A result of `0xffffffff` returns `0` without opening the bitset wrapper. Otherwise, the function obtains the catalog context at world offset `+0x10d8`, requests a `0x7d0`-byte view, and sets the mapped bit when the index is less than `0x3e80` (16,000). The setter returns `1` for every non-sentinel mapper result, including indices outside that range.

Static tracing of `0xab2940` recovers the mapper expression: it reads `ItemParam.RemakeID` through field hash `0xcb5eb33f` (the local schema identifies this as signed 16-bit `RemakeID`), rejects a negative value, then calls `0xf5ab10`. That helper returns `RemakeID * 8 + (byte_from_0xab0f50 & 7)`; if `0xab0f50` returns null, the low three bits are zero. The expression allocates eight possible catalog indices per `RemakeID`, consistent with the setter's 16,000-bit capacity. The meaning of each low-bit variant and the concrete item rows that select it are not established yet.

The source table join now confirms the layout behind those IDs: all 654 distinct nonnegative `ItemParam.RemakeID` values have an `ItemRemake.UniqueID` row. Of 1,044 ItemParam rows with a remake ID, 654 match that row's `ItemUniqueID`; the other 390 are the additional `Bromide` entries sharing RemakeID 652 and base ItemUniqueID 6426. All 391 rows in that group are `NotSee`. The ItemKind table maps these 1,044 rows to `ItemRemakeType` categories: 1,022 `Ftr`, 20 `Tool`, and 2 `Smartphone`. This is table-level grouping evidence, not proof that the game suppresses those rows from acquisition or registration.

Static tracing of `0xab0f50` shows that it conditionally returns a pointer to the packed item record at `item + 0xc`; `0xab2940` then reads that byte and masks it with `& 7`. The item record is copied by `0xf589b0` as an 8-byte payload, so the selected byte is payload offset `+4`. `ItemKind.ItemRemakeType` and `ItemRemake` pattern fields distinguish furniture, tools, and smartphone paths, but the exact user-visible color/design meaning of each payload value is still unresolved. Reproduce the table joins with `catalog_itemparam_table_audit.py` and inspect `item_remake_crosswalk` in its JSON output.

The resolved 1.0.0 `ItemParam` has 8,208 rows; 1,044 rows have nonnegative `RemakeID` values, across 654 distinct IDs (maximum 901). One striking group is `RemakeID=652`: 391 distinct `Bromide` rows, each with a distinct `UniqueID`, all have `ItemCatalogType=NotSee`. This may explain why they share a coarse mapping, but it does not prove whether the acquisition caller skips these rows or how their catalog state is used. The observed table's raw BCSV SHA-256 is `89230e97fc877ff2b2b48ac1c707ef32b3a7760118839c307f19797e2553458c`.

`tools/catalog_bitset_native.py` runs the original `0xeecad0`, `0xab2940`, and `0xf5ab10` instructions. It exhausts all 16,000 valid `(RemakeID 0..1999, low bits 0..7)` combinations, then checks sentinel/invalid-item, missing variant-byte, and out-of-range cases. Every case checks the return value and all 500 words of the 2,000-byte bitset; 16,011 controlled cases have zero mismatches. Stubs supply item validity, the ItemParam row and field lookup, variant-byte pointer, and save/context wrapper. This proves the native mapper and bitset arithmetic, but it does not exercise actual ItemParam rows or establish the semantic names of the low bits.

`tools/catalog_bitset_roundtrip_native.py` adds a paired native test for `0xeecad0` and the readback helper `0xeecba0`. Across 13 boundary, missing-variant, invalid-item, and neighboring-variant cases, the native getter sees the bit set by the native setter with zero mismatches. Both use the same mapped index and 2,000-byte synthetic manager. The ItemParam and save/accessor boundaries remain stubbed; this proves setter/getter consistency on a fixture, not persistence through a live save.

Run it with:

```sh
PYTHONPATH=/workspace/acnh-re/.deps python acnh-re/tools/catalog_bitset_native.py
```

The generated record is `output/gameplay/catalog_bitset_native.json`.

## Static trigger evidence and open work

- **[PSEUDO] Acquisition path:** `0xeebe80` validates/converts an item, conditionally calls `0xeecad0`, then passes through `0xf57920` and `0xf57880` for two additional `0x754`-byte bitset views. When the first helper reports no change and the second reports a change, it calls `0xeec010`. The call order is visible; the exact semantic meaning of each view and save-backed state is not established by this trace.
- **[NATIVE STATIC] Setter/readback pair:** `0xeecad0` writes a mapped bit at context offset `+0x10d8`; `0xeecba0` calls the same mapper and reads the corresponding word/mask from the same context offset. Both reject a sentinel mapping and guard indices at 16,000. The round-trip fixture above confirms their shared arithmetic and in-memory access, but the save key and serialization boundary are still not demonstrated by this fixture.
- `0xeec010` references `MarketBuiltMyVillage` and `FillCatalog`, then invokes the catalog fill writer when those checks pass.
- **[PSEUDO] FillCatalog progress count:** `0xeec760` reads a separate bitset at world offset `+0x1068`, intersects it with two selector bitsets (constructed with values 0 and 1), masks the final word to 24 bits, and sums popcounts across the resulting 15,000 valid bits. `0xeec010` passes this count to `0xf62b50` under `FillCatalog`. The relationship between this `+0x1068` set and the `+0x10d8` setter tested above, and the meaning of the two selectors, remain open.
- `0xeec0b0` and `0xeec280` call `0xeecad0` on conditional acquisition paths and update a second item bitset through `0xf57920`/`0xf57880`. Their exact conditions and bitset meaning still need a complete caller-level trace.
- `0x118a8a0` writes `BuyItem`, `HowmuchBuyItem`, and `BuyItemCatalog` achievement counters from a purchase-page callback. This proves the page's achievement updates, not delivery or mailbox timing.
- `0xa1bda0` is reached from the `0xa18db0` initialization chain and references the `MailboxCatalog` key, but the mailbox catalog's save transitions and delivery behavior remain unresolved.
- **[EF] Nook Stop catalog-mail flow:** `Obj_RcoMachine:RcoMachineOnlineShopping` starts with `UICatalogHandling`. Its `IsDeliveryToOthers` branch can enter `DeliverVillager`, where the user selects a resident, selects/edits a message card, saves the `cMsgCard` UI result, then runs `CatalogMailSend` and restarts the catalog UI with `IsSent=true`. The alternate/cancel route restarts with `IsSent=false`. The `CatalogMailSend` handler has a native factory/constructor/vtable mapping; a class-specific method at `0x33a570` references `SendLetter`, calls `0xf62e90`, and copies mail data through `0xf73ea0`. The resolver leaves the method slot's exact role unresolved, and this trace does not prove when an item arrives in the recipient's mailbox.
- The same entry checks `cLifeSupportAchievement:BuyItemCatalog` at border `100`; when `cPlayer:MainmenuOnlineShopping` is OFF it sets that player flag, installs application `cCatalog`, and queues `Player_GetDemo_Once:Get_ShoppingAppli`. This maps the app unlock threshold, not the per-item order rules. The extracted sequence and handler metadata are in `output/gameplay/catalog_order_flow_audit.json`, generated with `python acnh-re/tools/catalog_order_flow_audit.py --output-root /workspace/acnh-re/output`.
- **[TBL] Mailbox catalog:** `ItemMailboxCatalogData.byml` contains 33 `mUniqueID` values. All 33 join uniquely to `ItemParam` rows with `ItemKind=HousePost`; 5 have `ItemCatalogType=NotSee`, and 28 have `ItemCatalogType=Sale`. This maps the table's contents only; it does not establish whether these are ordered items, how they become available, or how delivery reaches the mailbox. Reproduce the join with `python acnh-re/tools/catalog_mailbox_table_audit.py --output-root /workspace/acnh-re/output`; output is `output/gameplay/mailbox_catalog_table_audit.json`.
- **[TBL] Item catalog classification:** across all 8,208 `ItemParam` rows, `ItemCatalogType` is `Sale` for 5,778, `NotForSale` for 1,043, and `NotSee` for 1,387. Nonnegative `RemakeID` counts are 348 `Sale` rows across 348 IDs, 283 `NotForSale` rows across 283 IDs, and 413 `NotSee` rows across only 23 IDs. This is a strong candidate for a display/registration distinction, but table values alone do not prove the native gate. Reproduce with `python acnh-re/tools/catalog_itemparam_table_audit.py --output-root /workspace/acnh-re/output`; output is `output/gameplay/catalog_itemparam_table_audit.json`.

The larger catalog queue item remains open. Concrete item-to-RemakeID/variant mappings for visible entries, the meaning of the low three bits, whether `NotSee` items are gated from registration, all acquisition triggers, save persistence, Nook Shopping order eligibility, and mailbox delivery require additional tracing and controlled native cases.
