# Catalog Bitset Native Follow-up

## Proven setter behavior

The native function at `0xeecad0` is the item catalog bit setter. It first calls `0xab2940` with the supplied item ID; the mapper's result is then used as the catalog bit index. A result of `0xffffffff` returns `0` without opening the bitset wrapper. Otherwise, the function obtains the catalog context at world offset `+0x10d8`, requests a `0x7d0`-byte view, and sets the mapped bit when the index is less than `0x3e80` (16,000). The setter returns `1` for every non-sentinel mapper result, including indices outside that range.

Static tracing of `0xab2940` recovers the mapper expression: it reads `ItemParam.RemakeID` through field hash `0xcb5eb33f` (the local schema identifies this as signed 16-bit `RemakeID`), rejects a negative value, then calls `0xf5ab10`. That helper returns `RemakeID * 8 + (byte_from_0xab0f50 & 7)`; if `0xab0f50` returns null, the low three bits are zero. The expression allocates eight possible catalog indices per `RemakeID`, consistent with the setter's 16,000-bit capacity. The ordinal is now linked to an item-specific display lookup key below; concrete item/ordinal-to-label pairs remain open.

The source table join now confirms the layout behind those IDs: all 654 distinct nonnegative `ItemParam.RemakeID` values have an `ItemRemake.UniqueID` row. Of 1,044 ItemParam rows with a remake ID, 654 match that row's `ItemUniqueID`; the other 390 are the additional `Bromide` entries sharing RemakeID 652 and base ItemUniqueID 6426. All 391 rows in that group are `NotSee`. The ItemKind table maps these 1,044 rows to `ItemRemakeType` categories: 1,022 `Ftr`, 20 `Tool`, and 2 `Smartphone`. This is table-level grouping evidence, not proof that the game suppresses those rows from acquisition or registration.

`tools/catalog_variant_mapper_native.py` now runs `0xab2940`, `0xab0f50`, and `0xf5ab10` against controlled synthetic `ItemParam`/`ItemKind` rows. Nine cases match the native mapper: a negative `RemakeID` returns `0xffffffff`; for a nonnegative ID, the resulting index is `RemakeID * 8` plus either the low three bits of the packed byte at item offset `+4` or zero when the relevant type/predicate does not select it. The fixture covers Ftr and Tool predicate-true/false branches, Smartphone kinds `0x6c` and `0x38`, an out-of-range `ItemKind` value, and `ItemRemakeType=None`. Item validity, table-row adapters, RemakeID access, and the Ftr/Tool predicates are stubbed, so the test validates mapper composition and byte masking, not the predicate rules or real per-item variants. Results: `output/gameplay/catalog_variant_mapper_native.json`.

The native `0xab0f50` control flow narrows those conditions further. `ItemRemakeType=Smartphone` exposes the payload byte only for `ItemKind` row indices `0x6c` and `0x38`; the resolved table labels both as Smartphone categories, while an out-of-range `ItemKind` value returns null. The Tool branch calls `0xaa7880`, which rejects row index `0x4e` and exposes the byte only when bit 8 is the first set bit in the 13-position vector returned by `0xa9e440`. The Ftr branch calls `0xaa84f0`, which reads the resolved `ItemKind.CanFtr` field (hash `0x90bc0855`); this identifies the gate as the item-kind furniture capability flag, though the mapper fixture still stubs that predicate. `0xf5ab20` consumes the 2,000-byte catalog bitset, enumerates absent indices within an item's eight-slot `RemakeID` range, chooses one absent variant with RNG, and writes the chosen low three bits through `0xaabf10`. Its caller `0xfa6380` is invoked by `0xfa60c0`, whose static trace updates `TodayGrowUp`, `BeyEvent_TotalPoint` thresholds at 100/200/300, and `BeyRequireFishSize`; this places the missing-variant selector on an event-point processing path, without proving that it is the only catalog acquisition source.

`tools/catalog_variant_selection_native.py` now executes native `0xf5ab20`, `0xab2810`, and `0xaabf10` on a synthetic 2,000-byte bitset and item payload. Five cases verify first/middle/last missing variant selection, a single remaining variant, and no setter call when all eight variants are present; all five match with zero mismatches. The deterministic RNG confirms rank `floor(random_u32 * missing_count / 2^32)`, and native `0xaabf10` writes the selected ordinal into the low three bits at payload offset `+4`. Item validity, RemakeID field adaptation, variant count, payload pointer, and RNG are stubbed; this is a native helper fixture, not a live-save or real-item run. Output: `output/gameplay/catalog_variant_selection_native.json`.


The catalog detail renderer adds a concrete UI binding for that selector. `0x118b6a0` shows the `STR_Remake_BodyColor` label for a remake-capable item and calls `0xab2700`; that helper formats a lookup key as `"%s_%05d_%d"`, with the last number read from the same low three payload bits. The byte therefore acts as a variant ordinal in the item-specific display key, not a directly decoded color name. The player-facing names still require matching message resources.

Static tracing of `0xab0f50` shows that it conditionally returns a pointer to the packed item record at `item + 0xc`; `0xab2940` then reads that byte and masks it with `& 7`. The item record is copied by `0xf589b0` as an 8-byte payload, so the selected byte is payload offset `+4`. `ItemKind.ItemRemakeType` and `ItemRemake` pattern fields distinguish furniture, tools, and smartphone paths, but the exact user-visible color/design meaning of each payload value is still unresolved. Reproduce the table joins with `catalog_itemparam_table_audit.py` and inspect `item_remake_crosswalk` in its JSON output.

The resolved 1.0.0 `ItemParam` has 8,208 rows; 1,044 rows have nonnegative `RemakeID` values, across 654 distinct IDs (maximum 901). One striking group is `RemakeID=652`: 391 distinct `Bromide` rows, each with a distinct `UniqueID`, all have `ItemCatalogType=NotSee`. This may explain why they share a coarse mapping, but it does not prove whether the acquisition caller skips these rows or how their catalog state is used. The observed table's raw BCSV SHA-256 is `89230e97fc877ff2b2b48ac1c707ef32b3a7760118839c307f19797e2553458c`.

`tools/catalog_bitset_native.py` runs the original `0xeecad0`, `0xab2940`, and `0xf5ab10` instructions. It exhausts all 16,000 valid `(RemakeID 0..1999, low bits 0..7)` combinations, then checks sentinel/invalid-item, missing variant-byte, and out-of-range cases. Every case checks the return value and all 500 words of the 2,000-byte bitset; 16,011 controlled cases have zero mismatches. Stubs supply item validity, the ItemParam row and field lookup, variant-byte pointer, and save/context wrapper. This proves the native mapper and bitset arithmetic, but it does not exercise actual ItemParam rows or establish the semantic names of the low bits.

`tools/catalog_bitset_roundtrip_native.py` adds a paired native test for `0xeecad0` and the readback helper `0xeecba0`. Across 13 boundary, missing-variant, invalid-item, and neighboring-variant cases, the native getter sees the bit set by the native setter with zero mismatches. Both use the same mapped index and 2,000-byte synthetic manager. The ItemParam and save/accessor boundaries remain stubbed; this proves setter/getter consistency on a fixture, not persistence through a live save.

`tools/catalog_unique_id_bitset_native.py` executes `0xa0f440` membership and `0xa0f510` set-bit logic on a 0x754-byte synthetic buffer. Ten boundary cases match exactly, including the highest accepted ID 14999 and rejection of the first padded bit at 15000. The data-pointer vtable and item-ID normalization helpers are stubbed, so the run validates the original bit arithmetic and 15,000-ID bound, not the save-key binding.

## Static trigger evidence and open work

- **[NATIVE STATIC] Unique-item set:** `0xeebe80` validates/converts the item, calls `0xeecad0` behind `0xab2a50`, then checks and updates the 0x754-byte view at context offset `+0x1068` through `0xf57920` and `0xf57880`. `0xf57920` reaches `0xa0f440`, which tests a bit by item ID; `0xf57880` reaches `0xa0f510`, which sets the bit and copies the 0x754-byte buffer back. Both helpers cap IDs at 15,000 (`ID >> 3 < 0x753`); the native boundary probe is documented above. When the pre-check is false and the update reports success, the caller reaches `0xeec010`. `0xeec0b0` and `0xeec280` use this same check/update path from separate item-add callers. The local save-key dictionary contains `SaveShopCatalog` and `SaveItemRemakeCollectBit`, which are plausible correspondences by name and index shape; the serialization layer has not yet tied either key to these wrappers.
- **[NATIVE STATIC] Setter/readback pair:** `0xeecad0` writes a mapped bit at context offset `+0x10d8`; `0xeecba0` calls the same mapper and reads the corresponding word/mask from the same context offset. Both reject a sentinel mapping and guard indices at 16,000. The round-trip fixture above confirms their shared arithmetic and in-memory access, but the save key and serialization boundary are still not demonstrated by this fixture.
- `0xeec010` references `MarketBuiltMyVillage` and `FillCatalog`, then invokes the catalog fill writer when those checks pass.
- **[NATIVE STATIC] FillCatalog progress count:** `0xeec760` reads the item-ID bitset at `+0x1068`, builds two `ItemCatalogType` selectors with values 0 and 1, intersects them with the collected-ID bits, masks the last word to 24 bits, then sums popcounts over 15,000 IDs. The schema enum order is `Sale=0`, `NotForSale=1`, `NotSee=2`, so `NotSee` entries are excluded from this achievement count.
